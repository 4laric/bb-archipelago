# The inputs bundle

`research/bb_inputs.db` — 18.7 MB, 35 files, sqlite with zlib blobs.

## Why it exists

Every tool that produces `research/joined/` or `research/catalog/` takes a path
to an extracted game dump. That works on the machine holding the dump and
nowhere else. So until now: the derived data in this repo could not be
regenerated by anyone else, could not be checked in CI, and could not be shown to
be what the tools actually produce. It was asserted, not reproduced.

`er-archipelago` hit the same wall and answered it with `gen_inputs.db`. This is
the same answer.

## Using it

```bash
python tools/bb_inputs.py --extract work/inputs      # needs only the repo
python tools/mine_param_joins.py work/inputs/params work/inputs/mined research/joined
git diff --exit-code research/joined                 # must be empty
```

You do not have to extract to answer a question. The bundle is plain sqlite, so
querying it directly is usually faster than unpacking 146 MB:

```bash
python tools/bb_inputs.py --get params/ItemLotParam.csv | grep '^4011,'
python tools/bb_inputs.py --list
python tools/bb_inputs.py --verify        # re-checks every sha256
```

Rebuilding needs the dump, and is the only step that does:

```bash
python tools/bb_inputs.py --build <path to the extracted game>
```

## What is in it, and what decides that

| prefix | files | what |
| --- | ---: | --- |
| `params/` | 4 | `ItemLotParam`, `NpcParam`, `EquipParamGoods`, `SpEffectParam` |
| `event/` | 27 | decompiled `*.emevd.dcx.js` |
| `mined/` | 4 | `msbb_miner` output — MSB treasures, enemies, regions, failures |

**Only inputs a committed tool actually reads.** `--check-coverage` scans
`tools/` for every `*.csv` it names and fails if the bundle is missing one, so
the bundle cannot drift away from the code that consumes it. Adding a param to a
tool reds that check until the bundle is rebuilt.

`mined/` is derived rather than raw — it is `msbb_miner` output. The MSBs
themselves are **not** bundled, so if the miner changes, regenerating that layer
still needs the dump. Everything downstream of it does not.

## The control that makes it trustworthy

A bundle you cannot check is a bundle you are trusting. The check is: **extract
it, re-run the derivation on an unmodified tree, and require an empty diff.**

That was run for this commit and it is now a CI job. Without it, "the bundle
reproduces the research" is a claim rather than a measurement — and the first
time the two silently diverge, every number downstream becomes unfalsifiable.

⚠️ Proving it required a fix. The tools wrote their JSON summaries with
`Path.write_text`, which applies platform newline translation — so the same tool
produced CRLF on Windows and LF on Linux, and the diff could never be empty
anywhere but the machine that last ran it. All summary writes are now pinned to
`newline="\n"`, and the committed files were normalised once. **The 13,811-line
churn in that commit is line endings only**; every file is byte-identical to its
predecessor once endings are normalised, which the commit demonstrates rather
than asserts.

## 🛑 This is extracted game data, committed deliberately

The repository's `.gitignore` previously said "do not commit or redistribute game
data" without qualification, and `research/mined/` is still excluded under that
rule for size reasons. This bundle is an explicit, narrow exception:

- it carries param tables, decompiled event scripts and MSB-derived tables from
  the owner's own dump;
- it exists so the derivation is reproducible, not so the game is distributable;
- **the repository is private.** That is load-bearing. Making it public is a
  decision about this file as much as about the code, and it should not happen
  by default.

Before widening the list, ask whether the addition is needed by a tool in the
repo. If the answer is "it might be useful later", leave it out — the coverage
check exists precisely so the bundle can grow on demand rather than on
speculation.

## Rebuild hygiene

The bundle is a binary blob, so every rebuild adds its full size to git history.
Rebuild when the tools need something new or the dump changes, not routinely.
`--list` shows a per-file sha256, so a rebuild that should have changed nothing
can be checked before it is committed.
